## analyze-complexity

問題の制約から許容計算量を逆算し、解法コードの計算量を積み上げで算出して、TLE/MLEにならないか判定する。

## 作業手順

### 1. 制約から許容計算量を逆算する

問題文の制約（Nの最大値、実行時間制限、メモリ制限）を確認する。AtCoderは通常 実行時間2秒 / メモリ1024MiB。
Rustは目安として **1秒あたり約10^8〜10^9回の単純演算**（定数倍が軽ければ10^9近くまで可能）。

| Nの最大値 | 許容される計算量の目安 | 典型的な解法 |
|---|---|---|
| N ≤ 12 | O(N!) | 順列全探索 |
| N ≤ 25 | O(2^N) | bit全探索、半分全列挙(N≤40) |
| N ≤ 100 | O(N^4) | 4重ループ、Floyd-Warshall(N^3) |
| N ≤ 500 | O(N^3) | 区間DP、Floyd-Warshall |
| N ≤ 5,000 | O(N^2) | 2重ループDP |
| N ≤ 2×10^5 | O(N log N) | ソート、セグ木、priority_queue、二分探索 |
| N ≤ 10^6〜10^7 | O(N) | 尺取り法、累積和、線形DP |
| N ≤ 10^9 | O(√N) / O(log N) | 試し割り、二分探索、ダブリング |
| N ≤ 10^18 | O(log N) / O(1) | 繰り返し二乗法、行列累乗、数式 |

複数の変数がある場合（N, Q, M など）は積で見積もる（例: Q回のクエリ×各O(log N) = O(Q log N)）。

### 2. コードの計算量を積み上げる

解法コードを上から読み、以下を積算する。

- **ループ構造**: ネストは掛け算。ただしループ変数の進み方に注意（`j += i` 型の内側ループは全体でO(N log N)＝調和級数、尺取り法の内側whileは全体で償却O(N)）
- **データ構造の操作コスト**（1操作あたり）:

| 操作 | 計算量 |
|---|---|
| Vec: push / pop / index | O(1)（pushは償却） |
| Vec: insert / remove（途中） | O(N) |
| VecDeque: push/pop（両端） | O(1) |
| HashMap / HashSet: insert / get / remove | 償却O(1)（最悪O(N)） |
| BTreeMap / BTreeSet / mylibのMultiSet: insert / get / remove / range先頭 | O(log N) |
| BinaryHeap: push / pop | O(log N)、peekはO(1) |
| sort / sort_unstable | O(N log N) |
| ac-library FenwickTree: add / sum | O(log N) |
| ac-library Segtree: set / prod | O(log N) |
| ac-library Dsu: leader / merge | ほぼO(α(N))≒定数 |
| String / Vecのclone、比較、ハッシュ化 | O(長さ) — **ループ内のcloneは見落としやすいので必ず数える** |

- **再帰**: 呼び出し回数×1回あたりのコスト。メモ化再帰は「状態数×遷移数」で数える
- **文字列・配列をキーにしたHashMap**はハッシュ計算がO(キー長)であることを忘れない

### 3. 償却・最悪ケースの区別

- 尺取り法・スタックを使う解法（ヒストグラム最大長方形など）・Union-Findは、1回の操作は重く見えても全体で償却される。「全体で合計何回進むか」で数える
- HashMapは敵対的入力で衝突しうるが、AtCoderのRustでは通常問題にならない。ただし不安なら`BTreeMap`のO(log N)で見積もる
- 最悪ケースを作る入力（全要素同値、単調列、スターグラフなど）で成立するかを必ず考える

### 4. メモリ量の見積もり

- 配列サイズ × 型サイズで概算する: `Vec<i64>`は8バイト/要素、`Vec<usize>`も8バイト、`Vec<Vec<...>>`はポインタ+容量のオーバーヘッド有り
- 10^8個のi64 = 800MB でMLE。**10^7個程度までが実用ライン**
- 2次元DPテーブルが大きい場合は、直前の行だけ持つ「配列の使い回し」で削減できないか検討する
- 再帰の深さがN（〜10^5以上）になる場合はスタックオーバーフローの危険を指摘する（`compete-new.sh`のテンプレートやスレッドスタックサイズ拡張の有無を確認）

### 5. 判定と報告

以下の形式で結論を報告する:

```
全体計算量: O(N log N)（内訳: ソートO(N log N) + クエリQ回×O(log N)）
最大制約での演算回数: 約 2×10^5 × 18 ≒ 3.6×10^6 回 → 2秒に対して余裕
メモリ: Vec<i64> 2×10^5個 ≒ 1.6MB → 問題なし
判定: 間に合う
```

ギリギリの場合（10^8〜10^9回）は「定数倍次第」と明記し、以下の定数倍改善候補を挙げる:
入出力のバッファリング、`sort_unstable`、HashMapをVecに置換、clone削減、modの遅延適用。
判定が不安な場合は実測（最大ケースを生成して`cargo run --release`で計測）を提案する。

## 注意

- 計算量の判定だけを求められた場合は、コードの修正はせず判定結果の報告のみ行う
- `mylib`のモジュールを解析した場合、確定した計算量を該当メソッドのコメントに反映することを提案する
